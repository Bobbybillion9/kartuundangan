# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Kartu Undangan" (kartuundangan.link) is an Indonesian digital wedding-invitation service. All copy is in Bahasa Indonesia. There is no build system or package manager — every page is plain HTML with inline/linked CSS and JS, deployed as static files plus a couple of Vercel serverless functions. There is no automated test suite.

The project has grown past the original single-file landing page: it's now a small multi-page app backed by Supabase (Postgres + Auth + Storage).

## Working with this codebase

- No compilation step for any page — edit the HTML/CSS/JS directly and open it in a browser, or serve the directory with a static file server, to preview changes.
- No linter, formatter, or test command configured — verify changes visually in a browser at both mobile (`max-width:960px`) and desktop widths, and in both light and dark theme.
- The Supabase project is live/shared — treat schema migrations and RLS policy changes as production changes, not local experiments.

## Structure of the project

- **`index.html`** — the public marketing landing page (theme gallery, pricing, FAQ, etc. — see "Content notes" below). Also hosts the shared login/signup modal (markup here, logic in `assets/app.js`), since it's the only page that has one — see `assets/auth-core.js` below.
- **`app.html`** — the private dashboard, reached only by an authenticated user. It has a sidebar/tabbar with 5 views (Home, Desain Kamu, Template Tema, Harga, Profil) plus an in-page **workspace editor** for a single invitation, itself split into 5 tabs (Isi Data, Desain, Pratinjau, Bagikan, Tamu & Ucapan). All driven by `assets/dashboard.js`. `app.html` has no login form of its own: on load it checks the session and, if there isn't one, redirects the visitor to `index.html` with the login modal opened (`#masuk`) and remembers where to send them back via `sessionStorage['ku-pending-return']` (same pattern as `PENDING_TEMPLATE_KEY` in `assets/app.js`); a `SIGNED_OUT` event while on `app.html` sends the user to `index.html` (no modal).
- **`undangan.html`** — the public-facing invitation page guests open (`/u/:slug`, rewritten by `vercel.json` to `api/u/[slug].js`). Loads the invitation row by slug, then renders it into an `<iframe>` pointed at the matching theme template (`templates/.../index.html`) and injects the couple's data into it (`assets/render-undangan.js`). Also wires up the guest-facing RSVP, Ucapan, and Hadiah (gift/transfer-proof) forms found inside the template markup.
- **`templates/`** — one subfolder per visual theme, each a self-contained `index.html` + `style.css` (own inline script for demo/preview behavior, overridden at runtime by `assets/render-undangan.js`). Organized by category, currently only `elegan-klasik/` (`ivory-gold`, `sage-rose`, `emerald-dusk`). More categories can be added later.
  - **Photo slots must ship empty.** Every `<img data-rv="img">` inside a photo slot carries no `src` and starts `display:none`, so the theme's own designed empty state (icon + "Foto Mempelai Pria" caption) is what shows until `setSlotFoto()` in `render-undangan.js` swaps in the couple's real photo. Do **not** bake demo photos into a theme's slots: sage-rose and ivory-gold used to, and since `templates/pratinjau.html` renders the raw template, every prospective customer previewing those themes saw the stock placeholders as if they were the design — which included a dog captioned "Foto Mempelai Pria" and a tennis court captioned "Foto Mempelai Wanita". The only image a theme folder should keep is `assets/thumbnail.jpg` (referenced by `THEME_TEMPLATES`) — the landing hero no longer pulls anything out of theme folders, so nothing else belongs there. Demo photos for the preview live in `templates/_demo/<theme>/` instead, one set per theme, loaded by `assets/demo-template.js` at runtime and never baked into the theme markup. `templates/pratinjau.html` renders any one theme standalone (used by "Preview" links and the dashboard's live preview tab).
- **`api/`** — Vercel serverless functions.
  - `api/u/[slug].js` — special-cases link-preview bots (WhatsApp/Telegram/etc.) with server-rendered Open Graph meta tags for a given invitation, and otherwise passes through to the static `undangan.html`.
  - `api/bayar/buat.js` — membuat tagihan Midtrans Snap. Dari browser hanya `invitation_id` yang dipercaya; siapa pemanggilnya dibuktikan dari token akses dan nominalnya diambil dari `api/_lib/harga.js`, tidak pernah dari body.
  - `api/bayar/notifikasi.js` — webhook Midtrans. Satu-satunya pembeda notifikasi asli dari POST buatan orang adalah verifikasi tanda tangan SHA512 di `api/_lib/midtrans.js`. Sengaja TIDAK mengaktifkan undangan otomatis — aktivasi tetap lewat tombol dashboard yang memvalidasi kelengkapan data lebih dulu.
  - `api/_lib/midtrans.js` — Snap token, verifikasi tanda tangan, terjemahan status, dan `KANAL_AKTIF` (daftar kanal pembayaran yang ditampilkan). Lingkungan sandbox/produksi ditentukan EKSPLISIT lewat `MIDTRANS_PRODUCTION`, tidak pernah ditebak dari bentuk kunci.
  - `api/_lib/harga.js` — harga versi server. Lihat catatan "Harga" di bawah: ini sengaja jadi tempat kedua, dan tidak boleh ada tempat ketiga.
- **`assets/`** — shared JS/CSS:
  - `auth-core.js` — creates the single shared Supabase client, session state (`KU.getSession()` / `KU.isSessionResolved()`), the `ku:session`/`ku:authevent` events other scripts listen for, and the generic Yes/Cancel confirm modal. Loaded by every page that needs auth.
  - `app.js` — index.html-only: the login/signup/forgot-password/recovery modal, the account dropdown/drawer, and the landing-page theme/pricing grids.
  - `dashboard.js` — app.html-only: sidebar/tabbar navigation, the auth guard described above, the workspace editor, and dashboard-side RSVP/Ucapan/Hadiah admin views.
  - `render-undangan.js` — shared by `undangan.html` (public guest view) and `templates/pratinjau.html` (dashboard preview): populates a theme template iframe with invitation data and wires up its guest-facing forms.
  - `theme-templates.js` — `THEME_TEMPLATES`, the single catalog of available themes (id, name, category, thumbnail, description). Used by both the landing page's theme grid and the dashboard's Template Tema grid. Add new themes here.
  - `pricing-plans.js` — `PRICING_PLANS`, the single catalog of Satuan/Berlangganan packages (name, price, features). Used by both the landing page's Harga section and the dashboard's Harga tab.
  - `hero-hp.js` / `hero-hp.css` — index.html-only: the hero's phone mockup that rotates through theme covers. The markup lives in `index.html`, not here — the first cover is the page's LCP image and must be in the HTML so the browser can start it before JS runs, and so the hero still renders whole if JS fails. The screens it shows are in `assets/hero/<theme>.jpg`, shot at 390×844 (real phone ratio); they are **not** the 2:3 `thumbnail.jpg`, which would get cropped inside a phone frame. Adding a theme to the hero means shooting a new one — the hero deliberately shows a curated three, not the whole catalog. Replaced `hero-corridor.js`/`.css` (nine cards flying at the reader), which turned into unreadable confetti at phone widths.
- **`tools/potret-tema.js` — run it whenever a theme's cover changes.** Two images per theme are not design assets but *screenshots of the theme's own cover*: `templates/<category>/<theme>/assets/thumbnail.jpg` (theme cards) and `assets/hero/<theme>.jpg` (the hero phone mockup). Any change to a cover's CSS, markup, demo photos, or monogram makes both stale instantly, and **nothing warns you** — the bug looks fixed in the real invitation while the old version keeps showing on the landing page and theme cards. That already happened: the white seam on the Sage Rose cover was fixed in CSS and gone from the live invitation, yet stayed visible on the homepage and in the theme card for hours, because those are pictures. The script needs the local static server on :5500 and headless Chrome on :9222; it waits for `#cover.has-sampul` (the flag `demo-template.js` sets once the cover photo has loaded) rather than a fixed delay, so it can't capture an empty cover.
- **`tools/cek-tema.js` — run it whenever you add a theme or change one's markup.** A theme has to satisfy a contract that is written down nowhere except inside the code that consumes it: the `data-slot` names `render-undangan.js` looks for, nine photo slots that each *wrap an `<img>`* (`setSlotFoto` sets `src` on the inner `<img>`, not on the container), the form ids it queries **from inside the `<form>`**, the two globals it calls afterwards (`buatMonogram`, `mulaiHitungMundur`), plus what `demo-template.js`, `potret-tema.js`, and `THEME_TEMPLATES` each expect. Break any one link and nothing throws — a mistyped slot simply never fills, a slot missing its `<img>` simply shows no photo, a `#rsvpMsg` that sits outside its `<form>` simply reads as `null`. The script loads each theme in headless Chrome and checks all of it, including behaviourally: it renames the couple and asserts the monogram initials actually change (deliberately not by id — two themes use `#monoLetterA/B`, one uses `.mono-a/.mono-b`), runs the countdown, and sets `--foto-sampul` to confirm the cover CSS really consumes it. It also flags catalog↔folder drift, demo photos baked into theme markup, and screenshots older than their source. Same prerequisites as `potret-tema.js` (:5500 + :9222); `--berkas` runs the file-level half without Chrome, `--rinci` lists passes too, and it exits 1 on any failure so it can gate a commit. The contract list inside it is a copy of what `render-undangan.js` does, so the script re-reads that file on every run and fails loudly if the renderer has grown a slot the list doesn't know about.
  - `demo-template.js` — index-independent: runs inside a theme document and fills its empty photo/music slots from `templates/_demo/<theme>/` so the standalone preview isn't all empty states. Never overwrites real invitation data — it checks the `window.__KU_DATA_ASLI` flag that `render-undangan.js` raises first.
  - `style.css` — shared design tokens and styles for `index.html`/`app.html` (spacing scale, radii, light/dark color tokens under `html[data-theme="..."]`, Fraunces/Inter fonts). Templates under `templates/` have their own separate `style.css` per theme.

## Backend (Supabase)

Project tables (all RLS-enabled):
- **`profiles`** — one row per `auth.users` id, extends it with `role`.
- **`invitations`** — the core row per wedding invitation: ownership (`user_id`), lifecycle (`status`: `draft`/`aktif`), the theme it uses (`kategori_desain`/`nama_desain`, matched against `THEME_TEMPLATES` — *not* a foreign key), the public `slug`, `sapaan_tamu` (`'personal'`/`'umum'` — apakah nama tamu dari link personal ditampilkan di sampul), and all the couple/event/content fields (names, dates, location, opening/closing text, photos, bank account info for the gift card). Insert/select/update/delete policies are all "own rows only" (`auth.uid() = user_id`). Akses publik TIDAK lewat policy select terbuka — lihat catatan RLS di memori project: yang dipakai fungsi `SECURITY DEFINER` (`ambil_undangan_publik`, `buka_undangan_tamu`, `cek_status_undangan`) yang menerima kunci spesifik dan mengembalikan paling banyak satu baris.
  Perpindahan `draft` -> `aktif` dijaga trigger `jaga_aktivasi_berbayar`: kalau `pembayaran_diwajibkan()` bernilai true, undangan wajib sudah punya baris `payments` berstatus `paid`. Gerbang itu **menyala** sejak 2026-08-27. Untuk mematikannya: `create or replace function public.pembayaran_diwajibkan() returns boolean language sql immutable as $$ select false $$;`
- **`rsvp`**, **`ucapan`**, **`hadiah`** — guest-submitted-per-invitation tables (RSVP responses, well-wishes, and gift/transfer-proof records respectively). Same RLS shape throughout: public `insert` gated on the parent invitation being `status = 'aktif'`, `select`/`delete` restricted to the owning `authenticated` user only (`ucapan` additionally lets the public `select`, since well-wishes are meant to be shown to other guests — `rsvp` and `hadiah` do not, those stay private to the couple). None of these have an `update` policy, by design.
- **`guests`** — satu baris per tamu yang dibuatkan link personal (`/u/<slug>?tamu=<kode>`), termasuk `opened_at`. Dipakai penuh oleh tab Tamu & Ucapan.
- **`payments`** — satu baris per percobaan bayar (`order_id`, `amount`, `status`, `tier`, `paid_at`, `notifikasi` JSONB berisi payload webhook mentah). Ditulis oleh `api/bayar/buat.js` (pending) dan `api/bayar/notifikasi.js` (paid/failed) lewat service role. RLS-nya cuma punya satu policy, `payments_select_own` — pemilik undangan boleh membaca pembayarannya sendiri. Tidak ada policy insert/update untuk siapa pun: menulis ke tabel ini HANYA boleh dari server yang sudah memverifikasi tanda tangan Midtrans.
- **`feedback`**, **`admin_requests`** — masih kosong dan belum dirujuk kode mana pun; kelihatannya rangka untuk fitur yang belum dibangun (formulir kontak, alur "minta dibuatin admin"). Jangan diasumsikan aman dihapus tanpa mengecek status terkini.
- **`templates`** dan **`invitations.template_id`** sudah **dihapus** — digantikan katalog JS `THEME_TEMPLATES`. Jangan ditambahkan kembali.
- **`profiles`** RLS-nya menyala dengan **nol policy**, jadi kolom `role` praktis tidak bisa dibaca siapa pun dari klien. Ini baru jadi masalah begitu ada fitur yang butuh membedakan admin — saat itu policy-nya harus dibuat lebih dulu.

Storage buckets:
- **`foto-undangan`** — public bucket for invitation photos (couple photos, gallery). Public because guests need to view them directly; path convention `[user_id]/[invitation_id]/...`, policies scoped to the authenticated owner for write/delete.
- **`bukti-transfer`** — private bucket for gift/transfer-proof photos uploaded by guests. Private because this content must stay visible only to the couple; path convention `[invitation_id]/[filename]` (no `user_id`, since anonymous guests uploading don't know it), matched against `invitations.user_id` via a subquery for the owner's read/delete policies. No `select`/`list` policy exists for anonymous guests, so a guest can upload but never see anyone's submission, including their own.

## Content notes

- `index.html`'s FAQ section's visible `<details>` content is duplicated in the `FAQPage` JSON-LD block in its `<head>` for SEO. If you edit FAQ questions/answers, update both places to keep them in sync.
- WhatsApp contact links across the site point at the real business number (`https://wa.me/628136372211`). If it ever changes, it is hardcoded in 6 places in `index.html` and 1 in `app.html` — there is no central constant for it.
- Pricing/feature copy is centralized in `assets/pricing-plans.js` (`PRICING_PLANS`) — when changing prices or features, that's the one place to edit; check for any hardcoded restatements elsewhere (hero note, FAQ answers, meta description) that might drift out of sync.
